# STM32F103 4G OTA 项目：难点、排查过程与解决方案

> 面试用复盘文档。每个问题按"现象 → 排查 → 根因 → 解决 → 结果 → 反思"来写。
> 时间线取自 2026-11-18 至 2026-11-20 的开发记录。文中的日志片段来自实际串口输出。

## 0. 项目背景（1 分钟版）

设备是一块 STM32F103C8 板子，通过 4G 模组（ML307R）连接 ThingsBoard 云平台，完成三件事：每 5 秒上报传感器数据、接收 RPC 控制继电器/LED/蜂鸣器、通过 MQTT 分包下载新固件并 OTA 升级。

难点集中在四个地方：

1. **串口不可靠的数据流**：模组应答和 MQTT 下行没有明确帧边界，分包是二进制，ISR / DMA / 任务之间怎么传数据要想清楚。
2. **裸机 → FreeRTOS 的迁移**：启动交接、中断优先级、共享总线、动态堆与任务拆分都要处理。
3. **OTA 的可靠性**：掉电、下载失败、校验失败、Bootloader 搬运失败，每种情况都要有明确状态。
4. **任务划分与优先级**：收包、下载、采集互相抢资源，拆错或优先级反了会直接导致丢包或“像死机”。

本文收录两个已解决问题，并在第 5 节单独总结任务设计（面试口述用）：

| 编号 | 现象 | 根因 | 解决 | 状态 |
| --- | --- | --- | --- | --- |
| P1 | 烧录后 `> Start APP...` 之后不动 | Bootloader 没关 SysTick，FreeRTOS 调度器启动前进入 SysTick 中断 | 应用 `main()` 开头关 SysTick、清挂起 | 已解决 |
| P2 | 连接时 `MQTT_CONNECT:` 匹配不上，等满 180 秒；其他协议解析也会出错 | 串口是字节流，没有可靠的帧边界；每批数据独立解析，未解析的半截数据被丢弃（拆包），一批里的多帧也分不开（粘包） | 累积并移动未解析数据，再按协议长度/关键字解析 | 已解决 |

## 1. P1：烧录后应用卡在 `> Start APP...` 之后

### 1.1 现象

- 烧录新的 Bootloader 和应用后，串口输出：

  ```
  > Start APP...
  ```

  之后没有任何输出。
- 后来加了 FreeRTOS，串口只多打印了一个 `>` 就停了。

### 1.2 排查

1. **对比输出位置**：`Start APP` 之后应用的第一个 `printf` 就不再输出，说明卡在应用启动的早期阶段，而不是后面的业务。
2. **检查 Bootloader 跳转前的状态**：Bootloader 用 SysTick 做 HAL 时基，跳转前没有关闭 SysTick，中断还在每 1 ms 触发一次。
3. **分析中断的归属**：应用加入 FreeRTOS 后，SysTick 中断被映射到 `xPortSysTickHandler`。调度器还没启动时，FreeRTOS 的任务链表是空指针（未初始化），第一次 SysTick 进入这个处理函数会访问空指针，触发 HardFault。
4. **和现象对上**：应用的初始化很快，第一个 SysTick 正好落在发送 `>` 的时候，所以只看到一个 `>`。

### 1.3 根因与解决

- **根因**：Bootloader 跳转时把 SysTick 留在运行状态，应用没有在启动时清理，FreeRTOS 调度器启动前就进入了 SysTick 中断。
- **为什么 Bootloader 会开 SysTick**：`HAL_Init()` 默认用 SysTick 做 HAL 时基。Bootloader 的重试延时（`HAL_Delay`）、W25Q 的忙等超时、Flash 编程的超时都依赖它，这是设计上需要的。问题在于跳转时没有把 SysTick 交还给应用。
- **解决**：在应用 `main()` 最开头（HAL 初始化之前）做三件事：

  ```c
  SysTick->CTRL = 0;                  // 关 SysTick
  SysTick->VAL = 0;
  SCB->ICSR = SCB_ICSR_PENDSTCLR_Msk; // 清挂起
  SCB->VTOR = FLASH_BASE | Application_1_Addr;
  ```

  调度器启动时，FreeRTOS 会重新配置 SysTick。这一处修改在应用里完成，没有重新烧录 Bootloader。

### 1.4 后续：误以为"又卡住了"

- 修复后再次烧录，串口只显示 `> W25Q32 OK`，之后没有输出，一度以为又卡住。
- 实际情况是：应用已经在正常运行（调度器启动、通信任务连接 MQTT），只是**我们在清理日志时把进度信息也删掉了**，`mqttConnect()` 最长阻塞 180 秒，期间没有任何输出。
- 为此加了三类诊断：`configASSERT` 失败时打印 `[ASSERT] 文件:行号`；`HardFault_Handler` 打印 `CFSR/HFSR/BFAR` 和出错的任务名；通信任务开始和连接结束时打印状态。

### 1.5 反思

- 裸机改 FreeRTOS 后，"启动交接"成为新的风险点。Bootloader 和应用各自对外设（SysTick、中断向量、时钟）的假设必须对齐。
- **静默死循环最难排查**：`configASSERT` 和 `HardFault` 原来都是死循环且不打印，任何错误都表现成"卡住"。调试期间必须有可观测的输出。

## 2. P2：协议粘包/拆包问题

> **问题描述**：串口是字节流，模组的应答和 MQTT 下行消息没有可靠的帧边界。接收端如果每次只处理当次到达的数据、不保留未解析的部分，就会出现**拆包**（一条消息被切成几段）和**粘包**（几条消息连在一起）。这会影响所有协议解析：AT 应答、MQTT 下行消息都受影响。

### 2.1 现象

- 2026-11-20 13:50 左右，设备连接 MQTT 时卡住：`AT+REST` 之后，`MQTT_CONNECT:` 一直匹配不上，等满 180 秒后失败。
- 串口里模组的应答是完整出现的，只是程序没有识别出来。
- 同样的问题影响所有经过这条接收路径的数据：AT 应答、MQTT 下行消息（RPC、属性、OTA 分包响应）。连接时的关键字只是最先暴露的一个。

### 2.2 排查

1. **看串口日志**：关键字被拆成两次取走，一次是 `MQTT_CO`，另一次是 `NNECT:123.57...`。两边单独看都不是完整的关键字，所以两边都匹配不上。
2. **对照接收代码**：每次取数后，解析只针对"这一批"数据。找不到完整关键字的那一段就被当作已处理丢弃，下一批到达的后半段也就无法和前半段拼起来。
3. **分析取数时机**：第一版取数的时机由"安静多少毫秒"决定。模组在单词中间停顿超过门限时，取数会落在关键字中间，把它切开。
4. **确认问题范围**：这条路径上的数据都是字节流，AT 应答和 MQTT 下行消息都会被同样切开。

### 2.3 根因与解决

- **根因**：取数之后不保留未解析的数据，每批数据独立解析；取数时机又由时间门限决定。关键字或一帧只要跨在两次取数之间，就无法拼接（拆包）；一批里有多帧时，又需要逐条拆开（粘包）。
- **第一版（失败）：只取不累计**。每次取到什么就立刻找关键字和帧，找不到就丢弃。问题不在取数时机本身，而在于取走的数据没有被保留，前半段在上一批里已经丢了。
- **最终：累积并移动未解析数据**。重写 `wifi4g.c` 的接收处理，对外接口（`wifiPoll`、`wifiCheckCmdStatus`、`gWifi4G`）保持不变：

  1. **累积并移动未解析数据**：取到的数据追加到 `wifiData` 尾部，解析基于累积的内容。每解析完一条（或确认一段文本已处理），用 `wifiShift()` 删掉头部，把未解析的半截数据前移到开头。这样尾部才能继续接收，半截数据也能留着等下一批补齐。
  2. **命令阶段（未连接）**：在累积数据里查找 `OK`、`MQTT_CONNECT:`、`ERROR`，数据被拆成几段到达也能匹配。
  3. **边界处理**：缓冲区满而没有匹配时，只保留末尾 32 字节，关键字可能正好跨在边界上。
  4. **发命令前清空**：`wifiFlush()` 在临界区内清空队列和累积缓冲，避免把上一条命令的应答当成本条的结果。
  5. **已连接阶段（按帧）**：`+MQRECV,[通道,]主题,载荷长度,载荷` 按头部声明的长度收齐后，整条交给 `mqttParse`；一批数据里有多条完整消息时，循环逐条处理。这一点同时解决了拆包问题，一批里的多条消息也能逐条拆开（粘包），不再依赖时间门限。
  6. **兜底**：不完整的消息等超过 500 ms 仍未凑齐就丢弃，避免占满缓冲区；头部格式错误时跳过标记，继续查找下一条。
  7. **附带收益**：统计 OK/ERROR 时只看消息之外的文本，避免固件二进制数据里碰巧出现的字节误导计数。

### 2.4 结果

修复后，一包 OTA 数据即使分几次到达，也能按长度收齐后再解析；`MQTT_CONNECT:` 也能正确匹配，OTA 下载成功，2026-11-20 14:02 确认升级可用。

### 2.5 反思

- 设计原则：先保留数据，再判断边界。取数和解析要一起设计，只取不保留，任何切分都会丢数据。
- 协议有长度字段就用长度判断帧边界；没有长度字段的文本（如 AT 应答）才用关键字匹配。
- "安静多少毫秒"只能碰运气，不能作为帧边界的依据。

## 4. 面试常见追问与回答要点

**Q1：你遇到的最难的问题是什么？**
- 讲 P2（协议粘包/拆包）。核心是串口是字节流，没有可靠的帧边界；解析只看当前这一批数据，未解析的半截数据被丢弃，关键字和帧一旦跨在两次取数之间就拼不起来，一批里的多帧也分不开。解决方法是累积数据并移动未解析部分，再按协议长度收帧。

**Q2：你是怎么排查的？**
- 先看串口日志，确认关键字被拆成几段（`MQTT_CO` + `NNECT:`）；再对照代码，看每批数据是否被独立解析、未解析部分是否被丢弃。P1 中则是通过输出位置和中断归属推断出启动交接的问题。

**Q3：为什么不用 DMA 的全传输完成中断来判断一包结束？**
- 4G 模组的 MQTT 下行消息长度不固定，也不一定以特定字符结束（分包数据是二进制）。协议头部有长度字段，所以用长度判断最可靠。

**Q4：FreeRTOS 迁移最大的坑是什么？**
- 启动交接（P1）：Bootloader 留下的 SysTick 在调度器启动前进入 FreeRTOS 的 handler，访问空链表触发 HardFault。另外是中断优先级：必须 ≥ 5 才能用 `FromISR` API。

**Q5：你是怎么处理静默卡死的？**
- 给 `configASSERT`、`HardFault` 加了打印，给关键步骤加了状态日志。静默死循环和"正在阻塞"在串口上无法区分，所以可观测性本身就是功能。

**Q6：如果重新做，你会改什么？**
- 一开始就保留未解析数据，按协议长度收帧，不依赖时间门限（对应 P2）。
- 诊断日志从一开始就分级（`[AT]`、`[UP]`、`[DOWN]`、`[OTA]`），并且二进制数据只打摘要（对应 P1 的排查）。
- OTA 一开始就拆独立任务 + 独立缓冲，避免 JSON 盖住分包、下载堵死收包。

**Q7：任务是怎么拆的？优先级为什么这样排？**
- 见第 5 节口述稿。

**Q8：用了哪些时钟和超时？周期怎么定的？**
- 见第 6 节；细节表在 `架构与设计.md` 第 16 章。

**Q9：同步、互斥、通知用了哪些？**
- 见第 7 节；完整表在 `架构与设计.md` 第 9 章。

## 5. 任务设计总结（面试口述）

> 详细表与时序见 `docs\架构与设计.md` 第 5 章。这里给**可直接背的短版**。

### 5.1 怎么拆（三个业务任务）

| 任务 | 职责一句话 | 为什么单独拆 |
| --- | --- | --- |
| **CommTask** | 唯一串口消费者：连接、解析、遥测、重连、发现 OTA 后通知 | `wifiData`/粘包状态机必须单消费者；再拆就要再加队列 |
| **OtaTask** | 下载状态机：擦写 W25Q、发分包请求、等 `recv_flag`、CRC、进度、复位 | 擦写等待较长；留在 Comm 里会停收包；App `waitReady` 已让出 CPU |
| **SensorTask** | 传感器 + 本地 GPIO（LED/蜂鸣器/继电器） | 通信/OTA 忙时仍要采集和心跳；RPC 只改寄存器，由 Sensor 周期刷输出 |

原则：**按资源边界和“谁会堵死谁”来切**，不按文件个数硬拆。

### 5.2 优先级（Sensor > Comm > Ota）

```text
高  SensorTask   idle + 2
    CommTask     idle + 1
低  OtaTask      idle + 0
```

| 关系 | 为什么 |
| --- | --- |
| **Sensor 最高** | Sensor 管心跳灯、传感器、本地输出——“设备还活着”。Comm 常长时间阻塞在 AT/`printf`/OLED；若 Sensor ≤ Comm，这些期间心跳和采集会停，像死机。Sensor 很轻（20/500 ms），抢占代价小。W25Q 等待在 App 已让出，但 Sensor 最高仍是现场保底。 |
| Comm > Ota | 擦写时仍要保证 Comm 能收包；App 的 `waitReady` 已 `vTaskDelay(1)` 让出，Comm 更高作双保险 |
| Ota 最低 | 下载是后台作业，可以慢，不能挡收包和采集 |

三句话记：Sensor 保现场，Comm 保收包，Ota 可以慢。

反例（面试常问）：
- Ota > Comm → 擦写时收包停滞，拆任务白做。
- Comm > Sensor → 下载/连网高峰传感器与心跳停更，像死机——这就是 Sensor 必须最高的反证。

### 5.3 任务之间怎么交互

```text
ISR ──通知──► Comm ──wifiPoll──► 解析
                 │
                 ├─ RPC ──写 REG_HOLD_BUF[0]──► Sensor 周期刷 GPIO
                 ├─ 遥测 ◄─读 REG_HOLD_BUF[1..7]── Sensor
                 └─ fw_* ──延时1s + 任务通知──► Ota
                                                │
                      Comm 写 chunk_buf + recv_flag ◄──► Ota 写 W25Q 后清标志
                      gOtaBusy：Comm 不停收包，但暂停遥测/重连
                      I2C1：Sensor / Ota(进度) / Comm(状态行) 用互斥量
```

缓冲隔离（和任务配套）：
- `mqttJsonBuf`：RPC/属性 JSON（Comm 用）
- `chunk_buf`：固件分包（Comm 写、Ota 读）；`recv_flag==1` 时不覆盖，写完 Flash 再清标志

### 5.4 30 秒口述稿

> 按资源边界拆了三个业务任务：Comm 独占串口接收解析，Ota 做固件下载写 Flash，Sensor 做采集和本地控制。优先级 Sensor > Comm > Ota：Sensor 最高是因为通信/擦写会长时间占 CPU，不抢占的话心跳和采集会停、像死机，而 Sensor 本身很轻；Comm 高于 Ota 是为了擦写时仍能收包。Comm 用任务通知启动 Ota，用独立 `chunk_buf` 传分包；Sensor 和 Comm 用寄存器表交换遥测与控制；I2C 用互斥量。

### 5.5 相关追问速答

| 追问 | 答法 |
| --- | --- |
| 为什么 Sensor 优先级最高？ | Comm/Ota 会长时间占 CPU（AT、擦写忙等）；不抢占则心跳/采集停，像死机。Sensor 很轻，抢占代价小。 |
| 为什么不把 OTA 放 Comm 里？ | 擦写忙等会停 `wifiPoll`，队列易满；拆开后 Comm 继续收，Ota 只做下载。 |
| 分包谁收、谁写 Flash？ | Comm 解析并写入 `chunk_buf`；Ota 等标志、写 W25Q、刷进度、算 CRC。 |
| 进度条谁刷？ | Ota，按已写字节累加百分比；百分比变化才刷 OLED，走 I2C 互斥。 |
| CRC 按包还是整包？ | 下载时累加全局 CRC，结束与服务器比对，再整镜像回读校验。 |
| 动态还是静态创建？ | 任务和 I2C 互斥量动态创建；堆 8 KB；`STATIC_ALLOCATION=0`。 |
| 还有什么风险？ | USART3 TX 无互斥，下载期 RPC 应答可能与分包请求交错；靠 `gOtaBusy` 降遥测冲突。 |

## 6. 时钟 / 定时 / 超时总结（面试口述）

> 完整表见 `架构与设计.md` 第 16 章。这里记**实现方式**和主干数值。

### 6.1 硬件时钟 + 两套时基

```text
HSE 8 MHz → PLL×9 → 72 MHz
  SysTick 1 kHz     → FreeRTOS（xTaskGetTickCount / vTaskDelay / 任务通知）
  TIM1 → 1 MHz → 1 ms → HAL（HAL_GetTick / HAL_Delay / 外设 Timeout）
```

**为什么拆开**：RTOS 必须占 SysTick；HAL 再用 SysTick 会和调度冲突。Boot 仍用 SysTick 做 HAL，跳转后 App 要先关（P1）。

### 6.2 等待怎么写（四种）

| 类型 | 怎么写 | 让出 CPU？ | 例子 |
| --- | --- | --- | --- |
| 任务阻塞 | `ulTaskNotifyTake` / `vTaskDelay` | **是** | Comm 收包、AT 等待、OTA 等包、W25Q `waitReady`(App) |
| RTOS tick 差分 | `xTaskGetTickCount() - t0` | 看循环里有没有阻塞 | 遥测 5 s、重连 60 s、OTA 开下前 1 s、分包 10 s 超时 |
| HAL tick / Delay | `HAL_GetTick` 差分或 `HAL_Delay` | **否**（忙等；更高优先级可抢） | 残帧 500 ms、AHT20 上电 40 ms、Boot W25Q |
| 硬件标志轮询 | 等 SPI/ADC 标志 | 极短空转 | `spiXfer`、`PollForConversion` |

要点：`AT+REST` 等 180 s **不是** `HAL_Delay(180000)`，而是「`wifiWaitRx(10)` 睡觉 + RTOS tick 判超时」。

### 6.3 主干数值

| 值 | 干什么 | 实现要点 |
| --- | --- | --- |
| **10 ms** | Comm / Ota / AT 轮询粒度 | 任务通知或 `vTaskDelay`，让出 |
| **20 / 500 ms** | Sensor GPIO / 采样 | `vTaskDelay` + tick 差分 |
| **5 s / 60 s / 1 s** | 遥测 / 重连 / OTA 开下前 | Comm 上 RTOS tick 差分 |
| **180 s** | `AT+REST` | RTOS tick 超时 + 内层让出 |
| **10 s × 3** | OTA 单包 | `vTaskDelay(10)` 轮询 `recv_flag` |
| **500 ms** | 残帧丢弃 | `HAL_GetTick`（在 Comm 循环里看） |
| **100 / 1000 ms** | W25Q 编程/擦除上限 | App：`vTaskDelay(1)`；Boot：忙等 |
| **40 / 80 ms** | AHT20 上电 / 测量 | `HAL_Delay` / 状态机看 `HAL_GetTick` |
| **1000 ms** | I2C/UART HAL 超时 | HAL 内部看 TIM1 tick |
| **≈4 s** | IWDG | 见下节计算；仅 Sensor 喂狗 |

帧边界：用 `+MQRECV` **长度**，不用“安静多久”；UART IDLE 只催促入队。

### 6.4 IWDG：超时怎么选、怎么算、哪里喂（口述）

**选型思考**（喂狗 = Sensor 约 20 ms 一次）：

- 正常余量很大；Sensor 偶发被 I2C/OLED/ADC 拖到几十～上百 ms。
- LSI 约 30～60 kHz，同一配置实际超时差约 ±30%～50%。
- **1 s** 偏紧易误复位；**2 s** 业务上更优；**4 s** 更稳（本工程先用）；**≥10 s / 180 s** 太慢，等于没看门——建链 180 s 时 Sensor 仍在喂，不必对齐 180 s。

| 标称 | 参数 | 计算（LSI=40 kHz） |
| --- | --- | --- |
| ≈2 s | `/128`，RLR=624 | \(128\times625/40000≈2\,\text{s}\) |
| ≈4 s（当前） | `/256`，RLR=624 | \(256\times625/40000=4\,\text{s}\) |

公式：\(T=\dfrac{\text{Prescaler}\times(\text{Reload}+1)}{f_{\text{LSI}}}\)。4 s 档在 LSI 偏差下大约 2.7～5.3 s。

| 步骤 | 谁做 |
| --- | --- |
| `main` 里 `MX_IWDG_Init` | 空操作（未允许启动），防初始化超时误复位 |
| `SensorTask` 入口 `IWDG_AppStart()` | 真正打开 IWDG |
| `SensorTask` 循环 `IWDG_AppRefresh()` | **唯一喂狗点**，约每 20 ms |
| Boot | 不开 IWDG |

### 6.5 30 秒口述稿

> 时基两套：SysTick 给 RTOS，TIM1 给 HAL。长等待一律任务阻塞或 `vTaskDelay`，所以 MQTT 建链 180 s、OTA 等包、W25Q 等 BUSY 都不空转。IWDG 用 LSI：256×625/40k≈4 s，只在最高优先级的 Sensor 每 20 ms 喂一次，调度起来之后才启动。

## 7. 同步 / 互斥 / 通知总结（面试口述）

> 详表见 `架构与设计.md` 第 9 章。

### 7.1 用了什么

| 手段 | 干什么 |
| --- | --- |
| **任务通知** | ISR→Comm 唤醒收包；Comm→Ota 启动下载 |
| **互斥量** | `i2c1Mutex` 保护 OLED/AHT20/INA226（`I2C1_Lock`） |
| **临界区** | `wifiFetch`/`wifiFlush` 出队，防 ISR 入队打断 |
| **自研 SPSC 队列** | `gQueueUart3`：ISR 字节入队 → Comm 出队（**不是** `xQueue`） |
| **标志协议** | `recv_flag`+`chunk_buf` 传分包；`gOtaFlag`/`gOtaBusy` 协调 OTA；`REG_HOLD_BUF` 无锁交换 |
| **vTaskDelay** | 周期与等包/等 Flash，让出 CPU，不是锁 |

### 7.2 没用什么

FreeRTOS `xQueue`、普通信号量、事件组；**USART3 TX 也没有互斥**（靠 `gOtaBusy` 降遥测冲突）。

### 7.3 一条链路背下来

```text
ISR 入队 + Notify → Comm 临界区取数 → 解析
  → RPC 写寄存器 / 属性置 gOtaFlag
  → 延时后 Notify Ota → Ota 等 recv_flag 写 Flash
  → 各方碰 I2C 必须 Mutex
```

### 7.4 30 秒口述

> 同步很克制：唤醒用任务通知，I2C 用一把互斥量，串口队列出队用临界区，OTA 分包用 `recv_flag` 握手，传感器和控制用寄存器表单写者免锁。没有上 FreeRTOS 消息队列。已知缺口是串口发送没有 TX 锁。
